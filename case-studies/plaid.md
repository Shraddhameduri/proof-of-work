# Plaid Python SDK: configuration keys that silently vanish

The Plaid Python SDK's `Configuration` class accepts credentials under only one exact spelling. Anything else — snake_case keys, different capitalisation, or idiomatic keyword arguments — fails, and most of those failures are silent: no error, just missing authentication headers. [plaid/plaid-python#587](https://github.com/plaid/plaid-python/issues/587) (open, filed 2026-09-03, no comments) asks for case-insensitive dict keys, snake_case fallbacks, and a kwargs-based constructor.

I reproduced the defect against plaid-python 45.0.0 (commit `69e13a88`) with a script exercising every mode from the issue. Five of six checks failed: `Configuration(api_key={'client_id': 'CID'}).auth_settings()` silently omitted `clientId`; `{'CLIENT_ID': ...}` returned `None` from `get_api_key_with_prefix('clientId')`; `Configuration(client_id='CID', ...)` raised `TypeError: __init__() got an unexpected keyword argument 'client_id'`; `api_key['client_id']` raised `KeyError`; and a mutation `api_key['CLIENT_ID'] = 'NEW'` was invisible through the camelCase lookup. The exact-camelCase baseline worked before and after. Silent auth failure is the worst kind for developers — nothing tells you the key spelling was wrong.

The root cause sits in one place. `__init__` stored `api_key` and `api_key_prefix` verbatim as plain dicts while `get_api_key_with_prefix` and `auth_settings` do exact-match lookups on camelCase security-scheme identifiers, so any variant spelling was silently dropped. A codebase-wide check confirmed nothing outside `configuration.py` reads `.api_key` directly, so fixing at the dict layer covers every consumer path without touching call sites.

Following the design sketched in the issue, I added a `CaseInsensitiveDict` that normalises string keys (lowercase plus stripping `_`/`-`) on every write and read, so `clientId`, `client_id`, `CLIENT_ID`, and `client-id` resolve to one entry. The `api_key`/`api_key_prefix` setters auto-cast plain dicts on assignment, and the constructor accepts `client_id`, `secret`, `plaid_version`, and `environment` kwargs merged with `setdefault`, so an explicit `api_key` dict still wins on conflict. `environment` accepts `sandbox`/`production` in any case, an `Environment` constant, or a literal host URL. I mirrored the identical logic in `templates/python/configuration.mustache` so a future OpenAPI-generator rebuild keeps the fix. Backwards compatible; no call-site changes needed.

After the fix the reproduction is 6/6 clean, and 29 new unit tests pass — covering key normalisation, all five issue modes including the issue's verbatim end-to-end example, and regressions (defaults, prefixes, `None` dicts, copy paths, kwarg-versus-dict precedence, environment resolution). The SDK's existing suite is live-integration only and requires sandbox credentials, so it wasn't runnable offline; a package smoke test confirmed the client builds and serialisation is unaffected.

Honest limits: iterating `api_key` now shows normalised keys (`clientid`); values and wire behaviour are unchanged, and nothing in the SDK iterates those keys. `environment` aliases only `sandbox`/`production`, anything else is treated as a literal host, and if both `host` and `environment` are given, `environment` wins. The template change is parity-only — not re-rendered here. No live API calls were made; header content was verified at the `auth_settings()` level.
