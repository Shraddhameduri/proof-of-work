# Scale AI MCP-Atlas: a benchmark fixture with no provenance

MCP-Atlas is a public benchmark of 500 agent tasks, and its README carries a smoke-test fixture: a prompt ("What is the first word of the file at /data/Barber Shop.csv?") with an expected answer ("Customer"). [scaleapi/mcp-atlas#84](https://github.com/scaleapi/mcp-atlas/issues/84) (open, filed 2026-09-15) asks three metadata-only questions: is that fixture independently synthetic, derived from, or identical to a released benchmark task — and if derived or identical, what is its stable task ID and dataset revision? Does any public, versioned, non-content-bearing provenance artifact exist that can answer that without opening task contents? And is there a versioned method to map the historical ten-row preview exposure to task IDs and dataset revision?

I ran a metadata-only audit — git objects, file scans, and dataset-card metadata; no benchmark task content was opened at any point. The finding is an absence, not a code defect. The fixture is byte-identical at the issue's pinned commit (`f24ba3fb`) and at HEAD, was introduced in commit `b8fffac` (2025-12-17), and its text has never changed since. But it carries **no stable task ID** — the population uses 24-character TASK IDs, and the fixture has none — and no dataset revision pin. A repo-wide scan for manifest, roster, attestation, or provenance artifacts returned zero hits; the git history and dataset card likewise document no preview release. And `run_eval.py` loaded the public split with `load_dataset("ScaleAI/MCP-Atlas", split="train")` and no revision argument — the split floats.

Validation confirms the picture: a checker fails 8 checks on the before state and passes all 10 on the after state (demonstrated via a stash/pop round-trip), including fixture-hash consistency, the pinned git objects, the honest verdict, and the no-invented-task-ID rule.

A new `PROVENANCE.md` records the fixture's git-established facts (introduction commit, pinned identifiers, the fixture section's sha256), the public split's point-in-time metadata (single `MCP-Atlas.parquet`, ~500 tasks, dataset sha `8c563b55…`, last modified 2026-08-03, CC-BY-4.0), states the three findings explicitly as NOT DETERMINABLE — no task ID is invented, and a validation check enforces that — and lists what the maintainers would need to add to close the gap (a fixture-generation manifest with fixture→task-ID mapping or a synthetic attestation, a versioned task-ID roster per release, a versioned preview mapping). Alongside it, `run_eval.py` now passes a pinned `DATASET_REVISION` to `load_dataset`, converting the floating public split into a versioned reference — one of the exact properties the issue asks for.

I'll state the limitation plainly: this is a finding, not a fix. Only the maintainers can supply the fixture-generation manifest or task-ID roster that would resolve it. The revision pin reflects the dataset's state on 2026-10-15 and must be re-pinned if it is re-uploaded. No task content was opened at any point, so every claim rests on git objects and public metadata.
