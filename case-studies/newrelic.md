# New Relic Python agent: parsing the whole CA store on every harvest

On Linux, the New Relic Python agent re-parses the entire system CA certificate store on *every harvest connection* instead of once per process. In the reporter's production profile (Django + gevent, py-spy over 300 seconds) the parse accounted for 10.55% of on-CPU time — the single largest self-time frame. [newrelic/newrelic-python-agent#1834](https://github.com/newrelic/newrelic-python-agent/issues/1834) (open, filed 2026-08-24, labelled `bug`).

I reproduced it with a local harness mirroring the harvest cycle: one long-lived `HttpClient`, `urlopen` against a local TLS server, then `close_connection()` — the harvest force-close that discards the pool so the next harvest rebuilds it — with `load_default_certs` wrapped to count calls and time them. Over 20 simulated harvests: **20 parses**, total parse time **0.663 s** (mean 33.2 ms each), loop wall **0.813 s** — roughly 82% of that loop was the parse. One full CA-store parse per connection, exactly as reported.

The root cause is two behaviours combining. First, `application.py` deliberately closes the collector connection after each harvest, so the next harvest constructs a brand-new `HTTPSConnectionPool`. Second, `HttpClient` only passes explicit `ca_certs` when the OS has no resolvable CA file; on typical Linux the default verify paths resolve, so no `ca_certs` is passed — and the vendored urllib3 then builds a fresh `SSLContext` per connection and calls `load_default_certs()` on each one.

The fix (+18 lines in `newrelic/common/agent_http.py`) builds the `SSLContext` once per `HttpClient` via the same `create_urllib3_context()` factory the per-connect path uses, calls `load_default_certs()` once, and passes it as `connection_kwargs["ssl_context"]`. The pool forwards it to every connection, which skips the reload branch. Socket close and reconnect per harvest are untouched — only the redundant certificate parsing is amortised. It applies only to the no-`ca_bundle_path` default Linux path, so explicit-bundle users keep byte-identical behaviour, and `disable_certificate_validation` still yields a `CERT_NONE` context. All four client subclasses inherit it.

After the fix: **1 parse** (at client construction), total parse time **0.041 s**, loop wall **0.082 s** — a ~10x reduction in this loop. I asserted behavioural equivalence explicitly: the shared context and a fresh per-connect context have identical `verify_mode` (CERT_REQUIRED), `check_hostname` (True), and CA store (122 certificates). The suite reports **62 tests passing** (59 pre-existing, 3 new covering the default, disabled-validation, and explicit-bundle paths), on commit `35ee5668`, Python 3.12.3, Debian-based Linux.

Honest limits: the harness proves the exact per-connection parse the issue names, but on a local test server — production ratios like the 10.55% figure depend on harvest frequency and the CA store. The shared context pins the CA set for the client's lifetime, so a mid-process CA rotation would no longer be picked up per connection; clients are recreated per application session, which bounds that. The explicit certifi-bundle fallback still re-parses per connection and was left out of scope.
